## 🧩 通用知识点 & 概念库

刷题过程中遇到的、不太熟悉的语法 / 概念，按主题归类，后续专题里遇到新的会持续补充在这里。

### 1. 循环边界条件的判断方法

> 💡 判断 `<` 还是 `<=`，本质是问自己两个问题：
> ① 这个边界值对应的位置，任务需不需要它？
> ② 这个位置之前有没有被别的逻辑处理过（会不会重复）？
> 不确定时，用一个最小的具体例子（如单行/单列矩阵）手动模拟一遍，比纯推理更快找到 bug。

### 2. `matrix.length` vs `matrix[0].length`

| 表达式 | 含义 |
| --- | --- |
| `matrix.length` | 外层数组长度 → **行数** |
| `matrix[0].length` | 内层数组（第 0 行）长度 → **列数** |

> ⚠️ **易错点**：这两个值都是「总数」，不是下标。只有需要「最后一个合法下标」时才 `-1`（如 `matrix.length - 1` 表示最后一行下标）。是否 `-1` 取决于你打算怎么用这个数，而不是它是行还是列。建议固定命名习惯：`let n = matrix.length`（行数）、`let m = matrix[0].length`（列数），避免像 `row`/`col` 这种容易和实际含义搞反的命名。

### 3. `break` 的作用范围

`break` 只会跳出**离它最近的那一层**循环，外层循环不受影响会继续执行。如果需要同时终止多层循环，单独用 `break` 做不到，需要借助标志位（flag）或把逻辑包进函数里用 `return` 直接跳出。

### 4. 变量作用域（Scope）与「循环外声明」的时机

> 💡 判断标准：**这个变量的值需不需要跨越多轮循环被记住/更新？**
>
> - 用 `let`/`const` 声明的变量，只在它所在的 `{}` 内存活，出了作用域就访问不到了（如 `return i` 在循环外访问循环体内声明的 `i` 会报错 `i is not defined`）。
> - **累加/累积模式**：像 `result ^= n`、`sum += n`、`max = Math.max(max, n)` 这类写法，要求变量必须声明在循环**外面**并用 `let`（不能用 `const`，因为 `const` 不能重新赋值）。如果声明在循环体内部，每轮都会被重新初始化，之前累积的结果全部丢失。

```js
// 常见累加器模式
let sum = 0;   for (const n of nums) sum += n;              // 求和
let max = -Infinity; for (const n of nums) max = Math.max(max, n); // 求最大值
let count = 0; for (const n of nums) if (条件) count++;       // 计数
let result = 0; for (const n of nums) result ^= n;            // 异或
```

### 5. `Set` vs `Map`：能不能解构遍历

| 结构 | 说明 |
| --- | --- |
| `Set` | 只存「单个值」，没有 key。`for (let item of set)` 每次拿到的就是那个值本身，**不能**写成 `for (let [a,b] of set)`（会报错，因为 item 不是数组，没法解构出两个变量）。<br>常用 API：`set.has(x)` 只能判断存在与否，**不能计数**。 |
| `Map` | 存「键值对」。`for...of` 遍历时每一项天生是 `[key, value]` 这样的二元数组，所以能用数组解构写成 `for (let [num, count] of map)`。<br>常用 API：`map.get(key)`（不存在返回 `undefined`）、`map.set(key, value)`（存在则覆盖）。 |

```js
// 用 Map 统计出现次数的标准写法
const map = new Map();
for (let n of nums) {
    map.set(n, (map.get(n) || 0) + 1);
    //          ^ map.get(n) 若为 undefined（没出现过），用 || 0 兜底
    //            否则 undefined + 1 会得到 NaN
}
for (let [num, count] of map) { ... }  // 数组解构，num=key, count=value
```

### 6. 数组解构赋值（Destructuring）

`let [a, b] = [1, 2]` 是按位置依次赋值的语法糖，等价于 `let a = arr[0]; let b = arr[1]`。同样的写法也用于交换两个变量：

```js
[matrix[i][j], matrix[j][i]] = [matrix[j][i], matrix[i][j]];  // 原地交换，无需临时变量
```

### 7. 异或运算（XOR）的核心性质

- `a ^ a = 0`（任何数异或自己等于 0）
- `a ^ 0 = a`（任何数异或 0 等于自己）
- 满足交换律和结合律（顺序、分组不影响结果）

> 💡 应用：数组中「只有一个数出现一次，其余都出现两次」→ 把所有元素依次异或，成对的数字两两抵消为 0，最后剩下的就是答案。O(n) 时间、**O(1) 空间**，是「哈希表统计」解法的空间优化版。

## Day5 矩阵 & 技巧 ✅

`73 矩阵置零` `54 螺旋矩阵` `48 旋转图像` `240 搜索二维矩阵 II` `136 只出现一次的数字`

### 核心知识点

- 矩阵题的空间优化，常见思路是「复用矩阵自身的某一部分（如第一行/第一列）当标记位」，避免额外开数组。
- 螺旋 / 边界收缩类问题的通用范式：维护 `left/right/top/bottom` 四个边界，每走完一条边就收缩对应边界；需要 `while(left<=right && top<=bottom)` 包住整体，并对「下边」「左边」两步做重复访问保护。
- 方阵原地旋转 90°：**转置（沿主对角线互换）+ 每行翻转**，转置时只处理 `j > i` 的部分，避免换了又换回去。
- 有序矩阵搜索：利用「行列均有序」的性质，从右上角（或左下角）出发单调移动指针，将 O(mn) 降为 O(m+n)。
- 只出现一次的数字：哈希计数解法 O(n) 空间 vs 异或解法 O(1) 空间，是同一问题的两种复杂度权衡。

### 通用技巧

| 技巧 | 说明 |
| --- | --- |
| 手动模拟小例子 | 不确定边界条件（`<` 还是 `<=`）时，用单行/单列/2×2 这种最小矩阵手动走一遍，比纯推理更快定位 bug。 |
| 命名规范 | 行数/列数固定用 `n`（行）/ `m`（列），避免 `row`/`col` 这种容易和实际含义搞反的命名。 |
| 指针移动方向判断 | 在有序矩阵/数组里做单调指针移动时，先想清楚「当前值偏大/偏小分别说明什么」，再决定指针往哪个方向收缩。 |
| 原地交换 | 用数组解构 `[a,b]=[b,a]` 做原地交换，不需要临时变量。 |

### 本专题踩过的坑

> ⚠️ 螺旋矩阵：内层循环下标行列写反（`matrix[right][i]` vs `matrix[i][right]`）；循环变量忘记自增/自减，导致重复 push 同一位置；进入新一圈时忘记把循环起点从写死的 `0` 改成当前边界值。

> ⚠️ 旋转图像：转置时内外层循环都从 0 开始遍历满，导致交换了又换回去；`matrix.reverse` 漏括号未真正调用，且翻转的对象弄错（应翻转每一行内部，而非翻转行的整体顺序）。

> ⚠️ 搜索二维矩阵 II：`while` 边界条件容易多减 1（如写成 `i < matrix.length-1`），导致最后一行/第一列被排除在循环之外，本质是把「判断这一轮该不该执行」和「预判 ++/-- 之后会不会越界」搞混了。

## Day6-7 链表 ✅（含 142 进阶）

`160 相交链表` `206 反转链表` `234 回文链表` `141 环形链表` `21 合并两个有序链表` `2 两数相加` `19 删除链表的倒数第N个结点` `24 两两交换链表中的节点` `142 环形链表 II` `138 随机链表的复制`

### 核心知识点

- **链表本质是一组通过指针（`next`）串联的节点**，没有下标访问，只能从头开始顺着 `next` 走，所以链表题的核心动作永远是「移动指针」和「改变指针指向」。
- **双指针（快慢指针）**：一个指针走一步，另一个走两步（或有固定间隔），常用于判断链表是否有环、找中点、找倒数第 N 个节点等。
- **虚拟头节点（dummy node）**：在头节点本身可能被删除/改变的场景（如删除节点、合并链表、两两交换），提前创建一个 `dummy.next = head` 的哨兵节点，可以避免对「头节点是否要特殊处理」写额外的 if 分支，统一逻辑。
- **反转链表**是链表题里最基础也是复用率最高的操作，很多题（回文链表、K 个一组翻转等）内部都会用到「反转某一段链表」这个子过程。
- **递归 vs 迭代**：链表天然具有递归结构（每个节点的 `next` 又是一个子链表），很多链表题既可以用迭代（循环+指针）解，也可以用递归解，需要能看懂两种写法并权衡空间复杂度（递归有调用栈开销）。

### 通用技巧

| 技巧 | 说明 |
| --- | --- |
| 画图模拟 | 链表题极度依赖「画箭头图」来跟踪指针变化，尤其是反转、交换类操作，强烈建议每写一步就画一下当前的指针指向，口算容易出错。 |
| Dummy Node | 只要涉及「头节点可能被删除或改变」的操作，第一反应就设置 `dummy`，用 `dummy.next` 最后返回真正的头节点。 |
| 快慢指针 | 找中点：慢指针走 1 步、快指针走 2 步，快指针到末尾时慢指针恰好在中点。判环：快慢指针从同一起点出发，若有环必相遇；找环入口需要额外的数学推导（第二次相遇点）。 |
| 先保存 next 再断开 | 反转/交换指针指向前，一定要先用临时变量保存原来的 `next`，否则改指针后会丢失后续链表的引用，导致链表「断掉」。 |
| 边界情况检查清单 | 空链表、只有一个节点、只有两个节点——链表题几乎都要过一遍这三种边界，很容易漏掉。 |

### 本专题踩过的坑

> ⚠️ **反复出现的高频错误**：`=`（赋值）和 `==`/`!==`（比较）混用，比如 `while(fast=slow)` 导致死循环、`ListNodeB==null` 误写成 `ListNodeB=null`；循环条件方向写反（如把「继续循环」的条件误写成「该停止」的条件，如 `while(left!==right)` 用在起点必然相等的场景，会导致循环一次都不执行）。

> ⚠️ 相交链表：双指针到达自己链表末尾后，误跳转到「此刻对方指针所在的位置」而不是「对方链表最初的头节点」，需要额外用不会变化的 `headA`/`headB`（函数参数本身，从未被重新赋值）作跳转目标。

> ⚠️ 反转链表：`let prev = curr.next; curr = prev` 这种「先改 curr 再赋值给 prev」的顺序错误，导致 prev 和 curr 指向同一节点；四步操作（存 next → 改指针 → 挪 prev → 挪 curr）顺序不能打乱。

> ⚠️ 回文链表（进阶）：快慢指针找中点的循环条件用「移动前检查」（`fast!==null && fast.next!==null`）而非「移动后检查」（`fast.next!==null && fast.next.next!==null`），对长度为 2 这类边界链表会导致 slow 多走一步，反转部分变空，比较循环被整个跳过、永远返回 true。

> ⚠️ 环形链表：起点必然相等，不能把「是否相遇」直接写进 `while()` 括号里判断（会在第一轮就被挡住不执行），需要用 `while(true)` + 内部 `if` 的结构，把「移动」和「判断相遇」拆开、保证移动发生在判断之前。

> ⚠️ 创建 dummy 节点时参数顺序搞反：`new ListNode(head, n)`（应为 `new ListNode(0, head)`），构造函数是 `ListNode(val, next)`，第一个位置永远对应 val，第二个位置永远对应 next，与传入的实参类型无关，只看位置。

> ⚠️ `let a, b, c = 1` 这种写法只有最后一个变量被真正赋值，前面的都是 `undefined`，JS 不支持类似 Python 的连续赋值语法。

> ⚠️ 两两交换节点：直接写 `root.left = root.right` 再写 `root.right = root.left` 会导致第一行赋值后原始信息被覆盖，第二行用到的已经不是「原始」的值——和交换两个变量的经典陷阱同理，必须先用独立的临时变量分别存好两个「源」，再各自赋值回去，顺序才不会互相干扰。

> ⚠️ 138 随机链表的复制：涉及「先建立映射再接指针」的两遍遍历模式，较绕，暂缓，后续找时间单独回顾。

## Day A 二叉树 ✅（124 待回顾）

`94 中序遍历` `104 最大深度` `226 翻转二叉树` `101 对称二叉树` `543 二叉树的直径` `108 有序数组转BST` `102 层序遍历` `98 验证BST` `230 第K小元素` `199 右视图` `114 展开为链表` `105 前序中序构造二叉树` `437 路径总和III` `236 最近公共祖先` `124 最大路径和（待回顾）`

### 核心知识点

- **三种 DFS 遍历顺序**：前序（根→左→右）、中序（左→根→右，对 BST 而言结果天然升序）、后序（左→右→根）。
- **递归解树类题目的核心三要素**：① 明确函数定义（传入一个节点，要返回什么）② 想清楚当前节点的答案如何由左右子树的答案推导/合并出来 ③ 想清楚终止条件（空节点该返回什么）。
- **「合并子树结果」型 vs「交换/改写」型**：像求深度、求直径这类题，是把左右子树各自的答案合并成当前节点的答案；翻转二叉树这类题，则是把递归处理好的左右子树直接交换位置挂回去，两种模式的代码结构相似但目的不同。
- **一次遍历顺便维护全局最优解**（如 543 题）：递归函数本身返回的是"深度"这类中间结果，但过程中可以顺便用一个声明在函数外部的变量，记录"经过当前节点的答案"并不断取最大值，这是"递归返回值"与"最终要的答案"不是同一件事时的常见处理方式。
- **判断"镜像对称"需要双参数递归**（101 题）：单参数的遍历只能站在一个节点上，无法同时掌握"另一侧对应位置走到哪了"，必须设计一个接收两个节点的辅助函数，且是"交叉"传参（左的左 配 右的右，左的右 配 右的左）。
- **验证 BST 需要传递上下界，不能只比较直接父子**（98 题）：BST 要求整棵左子树 < 根 < 整棵右子树，不是只看直接孩子，需要用 (min, max) 区间一路向下收紧传递。
- **层序遍历（BFS）用队列，不是递归**（102 题）：是本专题里唯一不是纯递归的题型，需要 `while(queue.length>0)` 外层 + 内层固定次数循环，逐层剥离处理。

### 递归模式总结（同一套四步法，"当前节点该做什么"这一步分七种情况）

| 模式 | 核心特征 / 例题 |
| --- | --- |
| 单纯遍历型 | 递归只负责"走一遍"，边走边收集结果，不需要合并左右子树的答案。例：94 中序遍历、230 第K小 |
| 合并左右结果型 | 递归返回值本身就是答案的一部分，当前节点答案 = 左右子树答案的某种运算。例：104 最大深度（取较大 +1）、543 直径（相加，顺便用全局变量记录最优解） |
| 交换/改写型 | 不是"算出一个值"，而是直接修改树结构本身。例：226 翻转二叉树、114 展开为链表 |
| 双参数比较型 | 单参数递归没法同时掌握"两个位置"的信息，需要设计成接收两个节点、成对同步递归。例：101 对称二叉树（交叉比较左的左 vs 右的右） |
| 携带约束条件下传型 | 除节点本身，还要往下传一个"限制条件"（上下界、数组区间下标等），每层根据当前节点收紧限制。例：98 验证BST（传 min/max）、105 前序中序构造（传数组区间） |
| 双重递归型 | 外层递归负责"枚举所有可能的起点"，内层递归负责"从固定起点出发计算"。例：437 路径总和III |
| 回溯判断型 | 先递归深入到底拿到左右子树各自结果，再根据结果组合情况反向判断当前节点该扮演什么角色。例：236 最近公共祖先（left && right 同时非空 → 当前节点是答案） |

### 通用技巧

| 技巧 | 说明 |
| --- | --- |
| 四步递归思考法（自创） | ① 找一个最小的、有代表性的局部结构（可画图辅助）② 想清楚这个局部里"当前节点"该做什么 ③ 想清楚子结构该交给递归哪次调用处理、参数怎么变 ④ 单独补上终止条件。不需要在脑内暴力推演整棵树，只想清楚"一层"该怎么处理，信任递归自动重复。 |
| 母题+变体识别法（自创，高效刷题核心方法） | 很多题本质是同一套骨架，只是在骨架的某个固定"插槽"里改了一行逻辑。遇到新题先问自己"这题的骨架我是不是见过"——见过就直接复用骨架，只想清楚新题在哪个环节加了什么新要求；没见过才需要重新搭骨架。典型例子：102 层序遍历（母题）→ 199 右视图（变体）：骨架完全一致，只在"处理节点"这一步加一行 `if(i===currLength-1)` 判断；104 求最大深度（母题）→ 543 二叉树的直径（变体）：同一套递归求深度的逻辑，只是顺便多维护一个全局变量；94 中序遍历（母题）→ 230 第K小元素（变体）：遍历逻辑完全不变，只是最后从结果数组里多取一个下标；206 反转链表（母题）→ 234 回文链表进阶解法（变体）：反转逻辑不变，只是起点和使用方式变了。 |
| 数组下标 vs 数组切片 | 108 题两种写法：`slice()` 每次切出新数组更直观但有复制开销；用 `left/right` 下标圈定同一个原数组的某一段，不复制、更省内存，是快排/归并/二分等经典算法的通用底层模式，值得优先吃透。 |
| 层序遍历的层数分离 | 进入内层循环前必须先把 `queue.length` 存进一个独立变量（如 `currLength`），因为这个数字之后不会再变化，循环体内不断有新节点被 push 进 queue 也不受影响；如果直接拿 `queue.length` 做循环判断条件，会被新数据污染，导致层与层混在一起。 |
| 队列的 shift/push 互不冲突 | 取（shift）永远从队头拿，放（push）永远加到队尾，两者操作的是队列的两端，不会互相干扰——这也是为什么"边取边放"能安全地在同一个循环里进行。 |
| 队列 API：push/pop/shift/unshift | 按「操作末尾用 push/pop，操作开头用 unshift/shift」记忆；层序遍历需要「先进先出」，必须用 `shift()` 取头部，用 `pop()` 会变成后进先出（栈的行为），顺序会错。 |

### 本专题踩过的坑

> ⚠️ 递归函数忘记加终止条件（`if(!node) return ...`），导致对 null 取属性直接报错——这是几乎每道树递归题第一次尝试都会漏掉的一步。

> ⚠️ 递归函数内部误用外层固定不变的 `root`，而不是当前层真正的参数（如 `node`），导致递归无法真正逐层深入，每层都在处理同一个顶层节点。

> ⚠️ 把自己写的递归函数（如 `maxDepth`）和 JS 内置的 `Math.max` 搞混，直接把两个数字传给自定义的递归函数求"最大值"，而不是调用 `Math.max()`。

> ⚠️ 求最大深度/直径时忘记 `+1`（当前节点自己也占一层），或者搞混"节点自身深度需要 +1"与"经过该节点的路径长度不需要 +1"这两个不同的量。

> ⚠️ 对称二叉树：一开始设计成单参数遍历函数，用 `root.left !== root.right` 直接比较两个不同的节点对象（永远为 true，因为比较的是引用地址），未能建立"双参数交叉比较"的正确模型。

> ⚠️ 全局累加变量（如 `maxD`/`maxDiameter`）忘记在函数外先用 `let` 声明，直接使用导致 `undefined` 参与运算变成 `NaN`。

> ⚠️ 层序遍历：`for` 循环条件写成 `i < levelSize.length`（levelSize 是数字，没有 .length 属性，结果恒为 undefined，循环条件恒为 false，内层不执行但外层死循环）；以及用 `pop()` 代替 `shift()` 破坏先进先出顺序。

> ⚠️ 验证BST：忘记递归调用中第二个参数应始终是 `node.val`（不是 `left.val`/`right.val`，因为 left/right 本身就是数字没有 .val 属性）；右子树递归时误传 `node` 自己而不是 `node.right`，导致递归无法真正深入；判断条件用 `<`/`>` 漏掉等于边界，应为 `<=`/`>=`（BST 不允许重复值）。

> ⚠️ 右视图：push 孩子节点时误写成 `queue.push(node.val)`（push 进去的是值不是节点），下一轮 shift 出来的是数字而非对象，取 `.val`/`.left`/`.right` 时报错或得到 undefined。

> ⚠️ 从前序中序构造二叉树：`slice` 切割左子树部分的终点边界容易搞错（`preorder.slice(1,mid+1)`，mid 既代表"根在中序里的下标"又被借用为"左子树节点数量"，两个数组里含义不同但数值相同，容易理解成"取到根节点"而误以为重复）；空数组判断误写成 `!preorder`（空数组是真值，不在 falsy 清单里），必须用 `preorder.length===0`，否则递归永远不会停止导致栈溢出；方法名大小写拼错（`indexOf` 误写成 `IndexOf`）。

> ⚠️ 路径总和III：内层 dfs 忘记终止条件（对 null 取 .val 报错）；`remain-root` 应为 `remain-root.val`；内层 dfs 末尾误写 `return root` 应为 `return count`；外层递归误用 `dfs(root.left,...)` 而非 `pathSum(root.left,...)`，导致只对根的直接孩子重新算了一次以其为起点的路径，却没有让这些孩子自己的子节点也被当作全新起点枚举到，会漏算路径（需要 outer 函数完整递归自己，而不是只调用内层 dfs 一次）。

> ⚠️ 最近公共祖先：容易把"终止条件"（root 是 null/p/q 时返回）误认为是"找到答案的核心逻辑"，实际上真正判断 LCA 的是 `if(left&&right)return root` 这一行——终止条件只负责"何时停止递归往上报告"，核心推理发生在回溯汇总的那一层；`return root` 里的 root 是当前递归层自己的 root（每层参数各自独立，同名不冲突），不是最外层传入的 root。

### 核心知识点（回溯部分）

- **回溯的本质是"做选择 → 递归 → 撤销选择"这一套通用骨架**，靠系统性地穷举所有可能的路径来找到全部答案；"撤销"这一步是为了保证某一条分支尝试过的东西，不会污染到它的兄弟分支。
- **两种主流写法，逻辑等价，区别只在"要不要手动撤销"**：一种是原地修改共享数组（`path.push(x); dfs(path); path.pop()`，46/39/17/131 的 start-i 写法都是这个模式），必须手动 `pop` 配对撤销；另一种是每次用展开运算符新建数组（`dfs([...path, x], ...)`，78 的选/不选写法、131 的选/不选写法），不碰原数组，天然不需要撤销。
- **结果收集的两种时机**：只在"选够/选满"的叶子节点收集一次（46 排列、17 电话号码、22 括号生成、39 组合总和、131 分割回文串——这几题的合法结果都要求"长度/总和恰好达标"）；每个节点都收集（78 子集——因为任意长度的组合本身就是一个合法子集，不需要等到某个特定终点）。
- **剪枝的本质是"提前判断，不合法的分支根本不调用 dfs"**，具体判断依据因题而异：78 用"有没有用过"（`includes`）、22 用"左右括号数量的大小关系"、39 用"当前和有没有超过目标值"、131 用"切出来的子串是不是回文"（调用一个外部判断函数）。
- **递归传参是 `i` 还是 `i+1`，取决于"这一步选完之后，同一个候选还能不能再选一次"**：39 组合总和允许同一个数字重复使用，所以传 `i`；78 子集、131 分割回文串每个位置只能用一次，所以传 `i+1`。
- **连续的多个 `if` 不是 `if/else`**：像 78、131 的"选/不选"写法里，两个 `if` 各自独立判断、条件成立就会执行，不存在"满足了第一个就跳过第二个"。第一个 `if` 里的 `dfs` 调用会完整探索完自己那整条分支（可能产生好几个结果）才会返回，程序才会往下走到第二个 `if`。
- **母题识别**：78 子集的"`start` 控制起点、只往后选不回头"是这几道题共享的底层结构；46 排列因为要考虑顺序（可以选任意还没用过的数），换成了"查重"而不是 `start`。一句话概括——**"能不能往回选"决定了骨架用查重还是用 `start`**。

### 通用技巧

| 技巧 | 说明 |
| --- | --- |
| 先问"骨架见过吗" | 拿到新的回溯题，先套自创的"母题+变体"方法：判断这题跟哪道见过的题骨架一致，只想清楚新题在哪个"插槽"（候选集合/终止条件/剪枝方式/传参）里改了逻辑，不需要每次从零搭骨架。 |
| 递归调用栈的直觉 | `dfs(...)` 这一行不是"调用完立刻继续下一行"，而是"整个跳进去，把这条分支能展开的所有可能都探索完"，中间可能还要再递归好几层，这一步没走完，外面的代码（比如 `pop()` 或下一个 `if`）都不会执行。 |
| 逗号的两种身份 | 函数调用括号 `()` 里的逗号永远是"参数分隔符"；数组字面量 `[]` 里的逗号永远是"元素分隔符"。两种逗号叠在一起用（如 `dfs([...arr,nums[index]],index+1)`）容易看串，要先按括号层级拆开再读。 |
| substring/slice 左闭右开 | `s.substring(start, i+1)` / `s.slice(start, i+1)` 都是"取到第二个参数之前"，所以要写 `i+1` 才能真正取到下标 `i` 这个字符本身；容易漏写 `s.` 前缀导致报错。 |

### 本专题踩过的坑

> ⚠️ 把该往 `arr` 里加的操作写成往 `ans` 里加（`ans.push(arr)` 而不是 `arr.push(num)`），导致 `arr` 永远是空数组、终止条件永远不成立，最终无限递归栈溢出（`Maximum call stack size exceeded`）。

> ⚠️ 变量名对不上号：定义的数组叫 `ans`，最后却 `return res`（`res` 从未定义）；类似的还有函数体内用了一个参数列表里根本不存在的变量（比如把 `right` 误写成 `i`）。

> ⚠️ 边界条件里 `ans.push(path)` 后漏写 `return`，代码会继续往下掉进 `for` 循环，此时下标已经越界，取值拿到 `undefined`，对 `undefined` 做 `for...of` 遍历直接报错。

> ⚠️ "选"和"不选"两行递归调用，**唯一相同的地方（`index+1`）反而最容易漏**：`dfs(arr,index)` 少加了 `+1`，导致"不选"分支永远在检查同一个位置，递归到不了终止条件，无限递归栈溢出。

> ⚠️ 共享数组污染：直接对同一个 `path`/`arr` 做 `push` 却没有配对的 `pop` 撤销（或者手误多 `push` 了一次），导致"选"和"不选"两条分支用的是同一个被污染过的数组，互相影响。

> ⚠️ 剪枝条件里拿一个固定值和一个变化的量比较（如 `if(right<n)`），而不是两个"同类型、都在变化"的量互相比较（应为 `right<left`）——某些测试用例可能侥幸通过，但剪枝逻辑本身是错的，起不到真正的作用。

> ⚠️ "剩余数量"和"已用数量"两种记账视角混用：变量定义成"剩余可用数量"（从 `n` 往下减），初始调用却还是传 `0,0`（应为 `n,n`），或者判断条件用了"已用"视角该有的写法。

> ⚠️ 运算符优先级陷阱：`!s[left]==s[right]` 里 `!` 的优先级比 `==` 高，实际执行的是 `(!s[left])==s[right]`，根本不是"判断两个字符不相等"，应写成 `s[left]!==s[right]`。

> ⚠️ 双指针函数忘记移动指针：`while` 循环体内只判断条件、没有 `left++`/`right--`，导致死循环。

> ⚠️ 混淆"多个独立的 `if`"和"`if/else`"：连续的 `if` 语句是各自独立判断、条件成立就会执行，不是"满足了第一个就跳过第二个"——第一个 `if` 里的 `dfs` 会完整探索完自己那条分支（可能产生好几个结果）才返回，程序才会往下走到第二个 `if`。

> ⚠️ 切割类问题里，一刀切下去之后，新窗口的 `start` 和当前位置为什么都设成 `i+1`：因为新窗口在还没扩展之前，天然只包含一个字符——"新窗口的起点"和"当前检查到的位置"此刻就是同一个下标，之后如果继续"不选"，两者才会拉开距离。
